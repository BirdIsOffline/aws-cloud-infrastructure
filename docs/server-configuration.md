# Server configuration baseline

The instance is stopped during CI-only publication preparation. Service health
and package versions below record the verified running baseline, not current
availability. Publication work does not start or reconfigure the server.

The automation has completed controlled deployment and strict configuration
idempotency testing on the lab server. Repeated execution preserved file content,
inodes, timestamps, ownership, permissions, package versions, services, and recovery
backup inventory. Terraform owns 33 AWS resource instances, including six delivery
security resources; these scripts own only operating system configuration and
website files. See the [resource inventory](../terraform/README.md).

The package-owned `/etc/nginx/nginx.conf` listens on port 80, uses server name
`_`, and includes `/etc/nginx/conf.d/*.conf`. Its existing main log format includes
remote addresses, requests, referrers, and user agents. Raw log events must remain
outside the repository and inspection reports. No HTTPS listener or additional
security response headers were observed. The managed drop-in preserves only
`server_tokens off;` and leaves the package-owned main configuration intact.

The current homepage retains its dark colors, responsive card grid, and inline
CSS. Its pinned release states that CloudWatch and Terraform integration are
complete and retains the earlier wording that CI/CD is planned. Authenticated
delivery has since passed end-to-end verification; this homepage copy is an
approved release snapshot, not the current implementation-status reference.
Changing it requires new release-hash approval. No CSS framework, JavaScript
runtime, build tools, or external web assets are required.

## Files and ownership

| Repository source | Linux destination / behavior |
| --- | --- |
| `website/index.html` | `/usr/share/nginx/html/index.html`, root:root 0644 |
| `config/nginx/security.conf` | `/etc/nginx/conf.d/security.conf`, root:root 0644 |
| `config/cloudwatch/amazon-cloudwatch-agent.json` | `/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json`, root:root 0644 |
| Agent cached JSON / TOML / YAML | Generated by the installed Agent tools; not repository source |
| Deployment backups | `/var/backups/aws-portfolio-lab/{website,monitoring}`, private root-owned directories |

Only these two Nginx files and one Agent source are managed. Package-default error
pages, logos, other configuration fragments, TLS material, IAM permissions, EC2
lifecycle, and Terraform state are not managed by the scripts. Existing target
files and the document root must not be symlinks. Scripts refuse unexpected Agent
fragments before using fetch-config, which can replace the active configuration set.

Existing managed files must be root:root with mode 0644; backup directories must
be root:root with mode 0700. The deployment scripts inspect numeric ownership and
mode before calling chown or chmod, including existing backup directories. Files
installed after a content change still receive the required metadata atomically.
Live repeat-run testing confirmed that compliant targets retained checksums,
inodes, mtime, and ctime without unnecessary service reloads or restarts.
Private temporary validation files and normal telemetry activity are expected.

## Monitoring contract

- Region `us-east-2`, namespace `AWSPortfolioLab`.
- Global, memory, and disk collection intervals: 300 seconds.
- Append `InstanceId` using `${aws:InstanceId}`; never embed an instance identifier.
- Memory measurement `mem_used_percent`.
- Disk measurement `used_percent`, resources `["/"]`, `drop_device: true`.
- Access and error files map to `/aws/portfolio-lab/nginx/access` and
  `/aws/portfolio-lab/nginx/error`, respectively, using stream name `{instance_id}`.
- Terraform owns seven-day retention. The repository Agent JSON intentionally
  omits `retention_in_days`; removing the old Agent setting is the only intended
  monitoring semantics change. No retention API is called by these scripts.

The original cached source included retention settings. Monitoring rollback
preserves its original JSON privately, but removes retention fields from the
rollback candidate so the Agent does not reclaim Terraform ownership. The scripts
never import or create infrastructure, change IAM policies, publish SNS messages,
or set alarm state. Agent operation naturally publishes metrics/logs and normal
HTTP checks create ordinary request log entries.

## Dependencies

The Linux scripts require Bash, root privileges, GNU coreutils, `cmp` (diffutils),
systemd, Python 3, Nginx, curl capability, and the CloudWatch Agent. AL2023 supplies
the standard OS commands. Bootstrap installs only missing nginx,
amazon-cloudwatch-agent, and python3 packages, plus curl-minimal only if the curl
command is absent. It also installs diffutils or coreutils if their required
commands are missing. It does not run a blanket upgrade or replace working curl.

Observed versions include Bash 5.2.15, Python 3.9.25, curl-minimal/libcurl 8.21.0,
OpenSSL libraries 3.5.8, PCRE2 10.40, and zlib 1.2.11. Nginx also depends on its
core/filesystem/mimetypes packages, libc, libcrypt, and libprofiler. RPM/DNF resolves
runtime dependencies; GCC is not required just because it built the package.

Existing installed packages are left at their current versions. Fresh package
installation uses the configured AL2023 repositories and may need dependency
transactions; it is not an exact-version lock. Verify package availability and
review package changes before testing on a fresh server. Required network access
includes package repositories when something is missing and AWS endpoints for
Agent validation/operation through the existing instance role.

## Security and deployment risks

The old `index.html.backup` was relocated intact to private storage outside the
document root during the approved deployment; its former URL returned HTTP 404.
The scripts do not create or relocate that legacy file. All new automation backups
are outside the public root.

Nginx headers/TLS, Agent least privilege, log permissions, backup retention, and
further hardening require separate decisions. The scripts retain the existing
runtime users and do not change log ownership, log rotation, security groups,
IAM permissions, or AWS encryption settings. Private backups and validation logs
can contain operational configuration and must never be copied into Git.

## Validation boundaries

Local Bash syntax, JSON/HTML checks, source inspections, LF checks, and help-only
execution do not prove Linux deployment behavior. Controlled server tests verified
Nginx configuration integration, Agent translation/schema checks, local/public HTTP,
service health, fresh metrics/log delivery, and strict repeat-run idempotency.
The hosted Linux harness passed 31 isolated recovery cases and two readiness
guards within 114 total tests. Live website restoration passed; Agent restoration
recovered healthy monitoring but did not complete its full verification and is
closed with limitations. The [testing record](recovery-testing.md) documents these
boundaries and the 225 separate private offline checks. An Agent activation may
regenerate cached/generated files or update metadata even with unchanged content;
that differs from a compliant no-op deployment, which must avoid activation.
Agent commands follow the installed toolchain and may make metadata/network reads.
