# Terraform infrastructure adoption

This directory defines infrastructure for the AWS Cloud Infrastructure, Security
& Automation portfolio project in `us-east-2`. All 27 networking, EC2, IAM,
CloudWatch, and SNS resources have been imported and verified with a refreshed
plan showing zero infrastructure changes. The existing server was subsequently
started with approval, and explicit public IPv4 assignment was verified through
two more refreshed plans. Both plans proposed only the public-address output
update described below. No apply or manual state update was performed. Further
AWS changes, imports, and plans require separate approval.

## Configuration

- `versions.tf` requires Terraform 1.17.2 or later within the 1.x series and the
  official `hashicorp/aws` provider within the 6.x series.
- `providers.tf` configures the AWS provider using the selected region.
- `variables.tf` defaults `aws_region` to `us-east-2`.
  It also pins `web_ami_name` to the exact discovered Amazon Linux 2023 image name,
  without wildcard matching or latest-image selection.
- `.terraform.lock.hcl` is generated by initialization and records the selected
  AWS provider version, currently 6.74.0, and integrity checksums. Keep this file
  in version control. Do not upgrade the provider during adoption.
- `vpc.tf` defines the VPC and its attached internet gateway, including VPC
  `prevent_destroy` protection during adoption.
- `subnets.tf` defines two public and two private subnets using stable map keys.
- `routing.tf` defines two route tables, the public internet default route, and
  four explicit subnet associations using standalone resources.
- `security-groups.tf` defines the web security group and separate ingress and
  egress rules without inline rules.
- `compute.tf` defines the EC2 instance and its root EBS settings, with read-only
  lookups for the exact Amazon-owned AMI and existing AWS-managed EBS KMS key.
- `iam.tf` defines the EC2 role, two standalone managed policy attachments, and
  instance profile. AWS-managed policy ARNs use the current partition and contain
  no account-specific identifiers.
- `cloudwatch.tf` defines the dashboard, CPU alarm, and two existing Nginx log
  groups with static `access` and `error` instance keys.
- `sns.tf` defines the notification topic and its separate policy. A read-only
  caller-identity lookup supplies the existing policy's account condition at
  runtime; no account value is hardcoded or exposed as an output.
- `outputs.tf` exposes resource references for later infrastructure components.
  No existing AWS identifiers are stored in the output definitions.

### Public IPv4 assignment resolved

The original launch explicitly enabled automatic public IPv4 assignment. The
approved restoration confirmed a public association on the running instance's
primary interface and successful HTTP access to the existing website. The
configuration now explicitly sets `associate_public_ip_address = true`.

In AWS provider 6.74.0, `associate_public_ip_address` is optional, computed, and
`ForceNew`. Its read logic records whether the primary network interface currently
has a public address association, rather than recovering the original launch
intent. The setting was initially omitted while the instance was stopped to avoid
an incorrect replacement proposal based on a computed value of `false`.

With the instance running, the refreshed baseline plan read the association as
`true` and proposed no infrastructure changes. The setting was then explicitly
enabled in `compute.tf`, formatting and validation passed, and a second refreshed
plan also proposed no additions, modifications, replacements, or destructions.
Both plans used `aws-lab`, `us-east-2`, provider 6.74.0, normal refresh, and
`-input=false -detailed-exitcode`.

Both plans returned exit code `2` because `web_instance_public_ipv4` changes from
an empty value to the currently assigned address. They also reported the
post-start public-address observation as external drift. This is an output/state
observation, not a request to modify AWS. The local state and its backup were
unchanged, so the output update remains unsaved. No address is recorded here.
Temporary ignored plan artifacts were removed after inspection. No apply was run.

The original launch intent is now explicitly managed without `ignore_changes`.
The subnet's public-IP auto-assignment remains disabled; the instance-level
setting preserves its original launch override. The assigned address is not an
Elastic IP and can change after a stop/start.

If the instance is intentionally stopped in the future, provider 6.74.0 may again
read its current public association as `false`. Review any resulting replacement
proposal as a lifecycle/provider observation issue, not permission to recreate the
server. Keep `prevent_destroy` enabled, retain the intended `true` setting, and
stop for separately approved investigation or restoration. Do not edit state,
configure `false`, or introduce an ignore rule to force a clean plan. No lifecycle
action is authorized by this documentation.

Provider behavior reference:
[AWS provider 6.74.0 EC2 source](https://github.com/hashicorp/terraform-provider-aws/blob/v6.74.0/internal/service/ec2/ec2_instance.go).

## CloudWatch and SNS adoption

The dashboard `AWSPortfolioInfrastructureMonitoring4` preserves all four metric
widgets. Every widget uses `timeSeries`, `stacked = false`, region `us-east-2`,
`y = 0`, and a `6 x 6` grid size. Instance dimensions reference `aws_instance.web`.

| Title | x | Metric | Statistic | Period | Additional settings |
| --- | --- | --- | --- | --- | --- |
| EC2 CPU Utilization | 0 | `AWS/EC2:CPUUtilization` | Average | 300 seconds | Left Y-axis |
| EC2 Memory Utilization | 6 | `AWSPortfolioLab:mem_used_percent` | Average | 300 seconds | Label `mem_used_percent` |
| EC2 Disk Utilization | 12 | `AWSPortfolioLab:disk_used_percent` | Omitted | Omitted | `path=/`, `fstype=xfs` |
| EC2 Network Traffic | 18 | `AWS/EC2:NetworkIn`, `NetworkOut` | Sum | 300 seconds | Preserve second-row shorthand inheritance |

The disk widget's omitted statistic and period are intentional. Do not add shared
widget defaults or rewrite metric dimensions during adoption. There are no log
query widgets or additional dashboard-level settings.

The untagged `aws-lab-high-cpu-alarm` monitors the lab instance's average EC2 CPU
utilization over 300-second periods. It preserves threshold `>= 80`, two
evaluation periods, two datapoints to alarm, missing-data treatment `missing`,
and enabled actions. Only the ALARM action references `aws-lab-alerts`; OK and
insufficient-data action lists remain empty. The description is
`Alerts when EC2 CPU utilization reaches 80% or higher for two consecutive 5-minute periods.`
The metric unit is deliberately omitted. A stopped instance can produce an
`INSUFFICIENT_DATA` state; alarm runtime state is not managed by Terraform.

The Nginx access and error log groups retain data for seven days, use class
`STANDARD`, have no tags or customer KMS key association, and leave AWS deletion
protection disabled. CloudWatch Logs still provides default encryption at rest.
Log names and class are replacement-sensitive, and reducing retention can delete
older events. Preserve these values during adoption; reported storage usage is
service-maintained telemetry and is not configured in Terraform.

The standard SNS topic preserves its empty display name, absence of tags, absence
of a configured KMS key, and absence of a custom delivery policy. The effective
service HTTP delivery defaults are not copied into an explicit custom policy.
Other service defaults, including the unreturned signature-version attribute,
remain unset during adoption rather than guessing new values.

The separate topic policy preserves version `2008-10-17`, the default policy and
statement IDs, AWS principal `*`, the original eight SNS actions, the topic
resource, and its owning-account `AWS:SourceOwner` condition. Its account value
and resource ARN are resolved through data and resource references. Do not add an
inline policy to the topic or manage the same policy through a second resource.

## Local validation

Run these commands from this directory with the installed Terraform executable:

```powershell
terraform fmt
terraform validate
```

The provider has already been initialized. On a fresh checkout, initialize from
the existing dependency lock file with `terraform init -lockfile=readonly`.
Formatting and validation do not import resources, compare against live AWS,
or confirm a change-free adoption. No import blocks or remote backend are included
at this stage. AMI, KMS key, partition, and caller-identity data source definitions
do not execute AWS reads during formatting or validation.

The VPC and EC2 `prevent_destroy` guards block planned destruction or replacement
while their resource definitions remain present. They do not protect against
deletion outside Terraform or deletion after a resource definition is removed.

Adoption is complete; do not repeat imports from a fresh checkout. Local state and
its backup are deliberately excluded from version control. Existing-environment
operations require the corresponding private state and a separately reviewed
workflow. Refreshed plans must be reviewed for unexpected additions, changes,
replacements, or destructions before infrastructure changes are considered.

The project `.gitignore` excludes Terraform state and state backups, local provider
files, variable files, saved plans with the `.tfplan` extension, crash logs,
override files, and local credentials. It leaves `.terraform.lock.hcl` available
for version control.
